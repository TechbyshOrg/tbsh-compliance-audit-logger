Compliance Audit Log

Compliance Audit Log (formerly Compliance Audit Trail & Evidence Logger) is a tamper-evident audit log for WordPress. It records who changed what on your site (people, AI agents, integrations and scheduled tasks) and proves that the record has not been edited since. On top of the log it adds incident response, governance registers, signed reports and read-only auditor access, to help you collect evidence for NIS2, DORA, ISO/IEC 27001 and SOC 2. The plugin supports your compliance work; it does not make a site compliant on its own.

Tamper-Evident Records

Every system transaction is cryptographically chained together using SHA-256 signatures, making unauthorized modifications or deletions immediately evident to security auditors.

Core Pillars & Features

  • Tamper-Evident Chaining: Standard database records can be easily modified or deleted directly via SQL. This plugin hashes each entry with the hash signature of the preceding log record, establishing an unbroken cryptographic chain.
  • Archival Evidence Vault: Automatically or manually capture full-system configuration snapshots (installed plugins, active themes, user roles, security configurations, database capacities) to serve as proof of system integrity during compliance audits.
  • GDPR Privacy Shield: Client IP addresses and User Agents are hashed locally and irreversibly using HMAC-SHA-256 with a unique, cryptographically random site salt. Complete support for core WordPress Personal Data Exporters and Erasers is included.
  • Local by Default: All log events, audit timelines, verification records, incidents, registers and snapshots are kept locally in custom SQL tables. No telemetry is collected. Outbound connections (alert channels, AI analysis, off-site vaults, WordPress.org core checksums) happen only after an administrator configures or triggers them.
  • Incident Response: Automatic incident detection, NIS2 Article 23 deadline tracking and multi-channel alerts (email, Slack, Discord, Microsoft Teams, Telegram, signed webhooks).
  • Governance Registers: A 5×5 risk register, a vendor / ICT third-party register (DORA Art. 28), a software supply-chain inventory and an operational resilience drill register with RTO/RPO.
  • Evidence & Reporting: An executive readiness score computed from real data, signed and verifiable compliance reports, encrypted off-site evidence vaults and expiring read-only auditor links.

One Plugin, Every Feature

Since version 2.0.0 the former separate edition is merged into this plugin. Every module documented here is included; there is no paid tier. Sites that used the separate edition are migrated automatically (see Migrating from the Separate Edition).

Getting Started & Installation

Follow these steps to deploy the plugin on your WordPress instance:

  1. Upload the tbsh-compliance-audit-logger directory to your WordPress site's /wp-content/plugins/ folder.
  2. Log in as an Administrator and activate the plugin through the Plugins page in the WordPress admin panel.
  3. Navigate to the new Compliance Logs sidebar menu to access the verification status, timeline, logs grid, and vaults.
  4. Go to Settings to customize logging thresholds, automatic evidence vault snap frequencies, and log retention parameters.
  5. Optional: configure alert channels, incident detection rules, AI analysis and retention in Settings, then add an off-site evidence vault.
  6. Recommended before saving any credentials: define a dedicated encryption key in wp-config.php (see Credential Encryption).

System Requirements

  • WordPress version 6.6 or higher.
  • PHP version 8.0 or higher.
  • MySQL / MariaDB database with standard transactional locking support.
  • Working WP-Cron (or a real cron job calling wp-cron.php) for alerts, retention and vault syncs.
  • PHP zlib for log archives and vault packages; the sodium extension is recommended (WordPress's compatibility library is used otherwise, more slowly); the ftp extension only for FTP/FTPS vaults.

How Things Work (Lifecycle & Flow)

The lifecycle of a logged event is built to maximize server efficiency while guaranteeing absolute cryptographic integrity:

  1. Event Capture: The plugin hooks into specific WordPress core actions (like logins, theme swaps, profile updates, and plugin upgrades) inside EventTracker.php and the focused trackers in Logging/Trackers/ (security, site structure and content). Bulk actions such as emptying spam or importing terms are summarised: more than five events of the same kind in one request become a single summary entry.
  2. Runtime Queuing: To avoid interrupting page rendering, the logged event is not immediately written to the database. Instead, it is appended to an in-memory runtime queue managed by Logger::$log_queue.
  3. Flushing at Shutdown: When WordPress triggers the PHP shutdown hook (meaning the page has completed loading and is rendered for the client browser), the queue is flushed.
  4. Sequential Chaining: During the database flush:
    • A lock is requested to prevent race conditions from concurrent sessions.
    • The verifier retrieves the signature hash of the last successfully logged event in the database.
    • The new row is inserted, and a combined canonical SHA-256 hash is computed using the record's values and the retrieved previous hash.
    • The row is updated with its calculated signature hash, making it an integral link in the cryptographic chain.
  5. Detection & Response: After each entry is written, the tbsh_cal_event_logged action fires. The incident detector and (when enabled) the behavioural anomaly detector listen to it, so detection reuses the events already recorded instead of hooking WordPress a second time. Opened incidents queue alerts, which are delivered later by WP-Cron.

When Things Trigger (Timelines & Crons)

The plugin manages background events dynamically:

  • Plugin Activation: Automatically builds/upgrades SQL schemas (and runs any pending migrations), generates a secure 64-character site salt for privacy masks, sets default logging preferences, grants all capabilities to administrators, schedules the cron hooks below, and registers the initial activation log event. Schema upgrades also run automatically after a plugin update, without reactivation.
  • Plugin Deactivation: Cleans up scheduled cron tasks and logs a warning event.
  • Plugin Uninstallation: Only if Delete all data on uninstall is selected in Settings, the plugin drops all of its tables (including leftover tables from the separate edition), deletes its options, capabilities, user meta, scheduled hooks and private files. Otherwise all data is kept.
  • GDPR Request Completion: When a user personal data erasure request is completed, the data is anonymized immediately, and a chain rebuild is triggered from the first altered ID onwards.

Core Architecture & Developers API

The logging engine is accessible to third-party integrations, allowing custom tracking parameters to be injected directly.

Programmatic Logging API

Developers can trigger compliance-focused events programmatically using the static Logger::log() method:

PHP API Usage 
use TBSHComplianceAuditLogger\Logging\Logger;

Logger::log(
    'config_alteration',                 // event_type
    'Configuration Management',          // event_category
    'warning',                           // severity (info, notice, warning, error, critical)
    'Security Constant Modified',         // event_title
    'Constant WP_DEBUG was modified.',   // event_message
    [
        'object_type'     => 'configuration',
        'object_id'       => 'WP_DEBUG',
        'compliance_tags' => 'ISO 27001 A.12, NIS2 Art 21',
        'metadata'        => [
            'previous_value' => true,
            'current_value'  => false
        ]
    ]
);

Public Logging API (recommended for other plugins)

Prefer the stable public API: it validates and sanitises input, reserves event types used by the detection rules (privilege_escalation, chain_compromised, file_edited and others), caps metadata at 8 KB and a request at 200 entries, and adds "source": "api" to the metadata. Call it after plugins_loaded.

PHP 
if ( function_exists( 'tbsh_cal_log' ) ) {
    tbsh_cal_log( 'invoice_approved', array(
        'title'       => 'Invoice approved',            // required
        'message'     => 'Invoice 1042 approved by finance.',
        'category'    => 'Change Management',           // one of the compliance categories
        'severity'    => 'notice',                      // info|notice|warning|error|critical
        'object_type' => 'invoice',
        'object_id'   => 1042,
        'metadata'    => array( 'amount' => '120.00' ),
    ) );
}

// Or without a function_exists() check:
do_action( 'tbsh_cal_log', 'invoice_approved', array( 'title' => 'Invoice approved' ) );

Cryptographic Hash Chaining & Verification

To protect records from unauthorized direct SQL manipulation, each database row is cryptographically linked to the previous row. A SHA-256 signature is calculated by combining row values with the preceding row's signature.

Canonical Hash String Structure

The verification engine compiles a canonical pipe-separated string from the database columns in the exact order below:

Hash Spec 
$canonical_string = implode('|', [
    $row_id,
    $row_uuid,
    $event_type,
    $event_category,
    $severity,
    $event_title,
    $event_message,
    $user_id,
    $site_id,
    $object_type,
    $object_id,
    $ip_hash,
    $user_agent_hash,
    $request_method,
    $request_uri,
    $metadata_json,
    $compliance_tags,
    $previous_hash,
    $created_at
]);

$integrity_hash = hash('sha256', $canonical_string);

Verification Logic

During an Integrity Scan, the verifier iterates through every log sequentially, recalculating the signature. If a row has been deleted, its ID sequence breaks, or if any cell is modified, the signature check fails immediately, flagging that specific ID and cascading failures down the rest of the trail.

GDPR Privacy Shield & Data Protection

Compliance logging requires recording the actor behind each event without violating strict data privacy laws. This plugin accomplishes this by employing irreversible local hash masking.

  • Salted Anonymization: IP addresses and User Agents are hashed locally using hash_hmac('sha256', $ip, $salt). The salt is generated on first activation using cryptographically secure random values and stored locally.
  • GDPR Exporter Integration: Registers the plugin with WordPress personal data exporters to gather all logging actions mapped to a user's email.
  • GDPR Eraser Integration: When personal data erasure is requested, the plugin anonymizes the actor columns (changing the username to "Anonymized User", user_id to 0, role to "none") and automatically rebuilds the cryptographic hash chain starting from that record to preserve audit trail integrity without breaking the chain.

Monitoring Features

What the plugin watches on your site, in plain terms. Event names and settings are listed in the Core Architecture and Settings Reference sections.

Activity coverage

Sign-ins and failed sign-ins, users, roles and capabilities (including Super Admin grants and capabilities granted outside the role menu), plugins and themes, edits made in the theme and plugin file editor, posts, pages and media, menus, widgets, Customizer and Site Editor changes, comments, categories and tags, settings, privacy requests, content exports, multisite network changes and application passwords. Bulk actions are summarised so the log stays readable.

WooCommerce

When WooCommerce is active, staff order changes, refunds, deleted orders, product price, stock and download changes, coupons and store settings are logged. Customer personal data is not logged.

Who made the change (AI agent attribution)

Every entry records who made it: a person, an AI agent, an integration, an automated task or a visitor, and how it arrived (browser, REST API, MCP, XML-RPC, cron or WP-CLI), with the application password and WordPress ability involved. A request counts as an AI agent when it arrives through an MCP server route or runs an ability with an application password. Ability runs that change the site are logged as their own entries, including refused and failed attempts; only input field names are kept, never values. Filter Activity Logs and exports by "Made by".

File integrity

WordPress core and plugins from WordPress.org are compared with the official checksums for their exact version. Other plugins, themes and must-use plugins are compared with a baseline recorded on the first scan and refreshed after updates. The uploads folder is searched for PHP files. Any change opens an incident. If you changed files on purpose, use "Accept current files" in the Integrity Center; large plugins are accepted in short steps with progress.

Active sessions

See who is signed in and on which device. During an incident, end a single session or sign a user out everywhere.

Logging exclusions

Silence routine activity from service accounts, roles or event types in Settings. Errors, critical events and security-relevant event types are always logged and cannot be excluded.

Setup Assistant

On a new install, a banner offers "Start setup". Pick the frameworks you work with, and the assistant applies recommended alerts, scheduled checks and retention periods in four steps. Every setting can be changed later.

SIEM forwarding and compliance digest

SIEM forwarding sends every new entry with its chain hash to an HTTPS endpoint, Splunk HTTP Event Collector or a syslog server over TLS/TCP, in order and within minutes; if the destination is down, entries are retried and an alert is raised after an hour. The compliance digest is a weekly or monthly email summarising activity, incidents and NIS2 deadlines, integrity and readiness, with a signed report attached as evidence of regular log review.

Site Network

See the readiness score, activity, errors, failed sign-ins, open incidents and log integrity of several sites running this plugin on one page. Connect each site with one of its own read-only auditor links; summaries refresh hourly and when you click "Refresh".

Incident Center & NIS2 Reporting

The Incident Center records security incidents with severity (info, notice, warning, error, critical), status (open, investigating, contained, resolved, closed), assignee, affected systems, root cause, impact assessment, compliance mappings, investigation notes and linked evidence snapshots. Incidents can be created manually or opened automatically.

NIS2 Article 23 Tracking

Mark an incident as significant (and optionally cross-border) to track the three NIS2 reporting stages, each with a status (pending, draft, submitted), submission time and authority reference. Deadlines are counted from the detection time:

  • Early warning: within 24 hours.
  • Incident notification: within 72 hours.
  • Final report: within 1 month (30 days).

Stages that pass their deadline without being submitted are flagged as overdue, and the daily maintenance run sends overdue reminders through the configured alert channels. A NIS2 Incident Report can be generated per incident and per stage from Compliance Reports.

Alerts & Notification Channels

Alerts are never sent during a page request. Each alert writes one queued row per ready channel to {prefix}tbsh_cal_alert_log and schedules a single tbsh_cal_dispatch_alerts event. Only alerts at or above alert_min_severity (default error) are queued, and identical alerts about the same subject are throttled for 15 minutes.

Risk, Vendor & Resilience Registers

Risk Register (5×5 Heat Map)

Each risk has a category (Operational, Technical, Compliance, Vendor, Security, Data Protection), likelihood and impact from 1 to 5, a score (likelihood × impact, 1–25), mitigation plan, owner, review date, status (active, mitigated, accepted, closed) and compliance mappings. The heat map plots active risks by likelihood and impact.

Vendor & ICT Third-Party Register (DORA Art. 28)

Record each supplier's service type, data access level (none, read, write), criticality and risk rating (low, medium, high), contact details, contract renewal date, security review date and status. A vendor can be linked to an installed plugin or theme slug. Active vendors whose renewal or review date is 30 or 7 days away trigger a reminder alert during the daily maintenance run.

Software Supply-Chain Inventory

Built from real site data: installed plugins and themes with their versions and pending updates (taken from WordPress's own update transients, so no extra request is made), their mapping to the vendor register, and every outbound integration you have configured (alert channels, AI provider, vault endpoints, WordPress.org). The inventory is cached for 12 hours and refreshed automatically when plugins or themes change.

Operational Resilience Drills

Plan and record drills by scenario (backup_restore, failover, incident_response, tabletop, other) with status (planned, completed, cancelled), scheduled and completed dates, RTO and RPO targets and actual values in minutes, outcome (passed, partial, failed) and notes. Resilience metrics summarise drill history and RTO/RPO results.

Executive Dashboard, Readiness & Analytics

The readiness engine is the single source of truth for the Executive Dashboard, Compliance Overview and reports. It runs pass / warn / fail checks against stored data (continuous logging, chain verification, core checksums, evidence collection, IP masking, alert channels, incidents and NIS2 deadlines, risks, vendor reviews and pending updates, off-site backups and resilience drills), produces an overall score with components, and shows framework coverage for NIS2, DORA, ISO/IEC 27001:2022 and SOC 2. Nothing is hard-coded: the score changes as your data changes.

Advanced Analytics

Event trends over 7 to 90 days (default 30).

Behavioural Anomaly Detection (opt-in)

When anomaly_detection is enabled, the plugin builds a 30-day baseline per user (usual hours, action mix, daily and hourly rates), refreshed daily. Each authenticated action is scored: unusual hour (+25, or +60 for a sign-in, so an odd-hour sign-in alone is logged), never-performed action (+40) or rarely performed action (+20), and a burst above the normal hourly rate (+25). Scores of 60 or more are logged as behavior_anomaly events; scores of 85 or more also open an incident. Users need at least 5 active days of history before they are scored. Baselines can be rebuilt on demand.

PDF uses the standard PDF fonts for Western European text. When a report contains other characters, it is generated again with an embedded subset of the bundled DejaVu Sans font, which covers Latin (including Central and Eastern European), Greek, Cyrillic, Armenian, Georgian and Vietnamese; the text stays searchable and copyable. Signing & Verification

Every stored report gets a SHA-256 content hash and an HMAC-SHA256 signature over that hash, keyed with a site secret derived from the plugin's encryption key. Verification recomputes both from the stored file, so any change to the file, or a signature produced without this site's key, fails verification.

Encrypted Off-site Evidence Vaults

Where: Evidence Vault → Off-site vaults tab (requires the tbsh_cal_manage_vaults capability). The receiving side of a remote-site vault is enabled under Settings → Off-site Vault Receiver.

Off-site vaults copy your evidence to storage the website cannot silently rewrite. Each sync builds a package containing the audit log rows added since the last successful sync, a full snapshot of the incident register and its notes, and the evidence snapshots captured since the last sync. The package is encrypted on your server before upload; the passphrase never leaves it.

ProviderFieldsNotes
S3-compatible (s3_compatible) endpoint, region, bucket, prefix, path-style, access key, secret key, passphrase AWS S3 (leave the endpoint empty; the region defaults to us-east-1), Google Cloud Storage (endpoint https://storage.googleapis.com with HMAC interoperability keys), Cloudflare R2, Wasabi, Backblaze B2, MinIO. Signed with AWS Signature Version 4; files over 8 MiB use multipart upload.
FTP / FTPS (ftp) host, port, mode (ftps default, or ftp), passive, path, username, password, passphrase Requires the PHP ftp extension. FTPS uses explicit TLS.
Another WordPress site (remote_site) receiver URL, receiver token, passphrase The other site must run this plugin with the vault receiver enabled.

Each vault has a schedule (hourly, daily or weekly), a Test connection action (writes and deletes a small probe file) and a Sync now action. Secret fields are write-only: they are never returned to the browser, an empty value keeps the stored one, and a field must be cleared explicitly to remove it. A failed sync logs vault_sync_failed (which can open an incident) and the vault retries hourly.

Vault Receiver

To accept packages from other sites, enable vault_receiver_enabled and set a receiver token in Settings. The receiver endpoint is POST /wp-json/tbsh-compliance-audit-logger/v1/vault-receiver. Requests are authenticated with X-TBSH-Signature = HMAC-SHA256(timestamp + "\n" + filename + "\n" + sha256(body), token), together with X-TBSH-Timestamp (max 5 minutes skew), X-TBSH-Filename and X-TBSH-Content-SHA256; replays are rejected. Packages up to 100 MB (filter tbsh_cal_vault_receiver_max_bytes) are stored encrypted in uploads/tbsh-compliance-private/vault-inbox/. The receiving site never learns the passphrase.

Package Format (.tbshvault, version 1)

File layout 
"TBSHVLT1"                         8 bytes (magic)
PBKDF2 iterations                  uint32 big-endian (210000)
salt                               16 bytes
secretstream header                24 bytes
repeated:
  ciphertext length                uint32 big-endian
  ciphertext chunk                 (64 KiB plaintext per chunk; last chunk tagged FINAL)

key    = PBKDF2-HMAC-SHA256(passphrase, salt, iterations, 32 bytes)
cipher = libsodium crypto_secretstream_xchacha20poly1305

Decrypted content: gzip-compressed JSON Lines, one record per line:
  {"type": "manifest" | "log" | "incident" | "incident_note" | "evidence", "data": {...}}
The manifest records the site URL, generation time, the last log ID before
this package (logs_after_id), the hash-chain head and the plugin version.

Keep the Passphrase Safe

A package cannot be decrypted without its passphrase, and the plugin cannot recover it. Store it outside the website (for example in a password manager).

Read-only Auditor Access

  • Create a link with a label and a lifetime of 1 to 90 days (default 7). The token is 256-bit random, shown once, and stored only as a SHA-256 hash with its last four characters as a hint.
  • The link /?tbsh_cal_audit=<token> is exchanged for an HttpOnly cookie and the browser is redirected to a URL without the token. API clients can send the X-TBSH-Auditor-Token header instead.
  • Auditor requests may only reach an allowlist of GET routes: dashboard, logs, timeline, evidence, integrity, compliance, readiness, executive, incidents (with notes and evidence), risks, vendors and supply chain, reports (list, download, verify), resilience drills and metrics, and analytics trends. Everything else is refused.
  • Invalid attempts are rate-limited per IP hash. Links can be revoked at any time; expired links are purged by the daily maintenance run.

Credential Encryption

API keys, webhook URLs, tokens and vault credentials are encrypted at rest with libsodium secretbox (XSalsa20-Poly1305) using per-purpose keys derived with HKDF-SHA256. They are never sent back to the browser.

By default the key material is your WordPress SECURE_AUTH salt, so rotating salts makes stored credentials unreadable (you would need to re-enter them). Define a dedicated key of at least 32 characters in wp-config.php to avoid this. System Health warns when no dedicated key is set.

wp-config.php 
define( 'TBSH_CAL_ENCRYPTION_KEY', 'replace-with-a-long-random-string-of-at-least-32-characters' );

Set It Before Saving Credentials

Adding or changing TBSH_CAL_ENCRYPTION_KEY after credentials were saved makes them undecryptable; re-enter them afterwards. The same key also signs reports, so reports signed under a previous key no longer verify.

Migrating from the Separate Edition

Version 2.0.0 replaces the separate edition of this plugin. Migration is automatic:

  1. Back up your database before updating.
  2. Update or install this plugin and activate it. If the separate edition is active, this plugin stays dormant for one request, deactivates the separate edition, and finishes setup on the next request.
  3. The migrator then:
    • renames the {prefix}tbsh_cal_pro_* tables to their new names (for example tbsh_cal_pro_alerts becomes tbsh_cal_alert_log). If a new table already exists, missing rows are copied over and the old table is kept as *_migrated_bak;
    • maps the old settings into tbsh_cal_settings, re-encrypts webhook URLs, bot tokens and AI keys into the encrypted credential store, and deletes the old settings option (it held plaintext secrets);
    • re-encrypts vault credentials. S3 and FTP vaults keep working when the old edition had an encryption password set (otherwise they are deactivated until you set a passphrase). Google Cloud Storage vaults become S3-compatible vaults and stay inactive until you enter HMAC interoperability keys. Remote WordPress vaults stay inactive until you enter the receiver URL and token. Azure and SFTP vaults are no longer supported and are deactivated; replace them with an S3-compatible, FTP/FTPS or remote-site vault;
    • renames capabilities (tbsh_cal_pro_* to their tbsh_cal_* equivalents) on every role, keeping custom grants;
    • converts auditor links to hashed tokens, so existing links keep working;
    • moves stored report files to private storage and logs a migration event.
  4. Review your vaults and alert channels, then send a test alert and run Test connection on each vault.
  5. Delete the separate edition from the Plugins screen while this plugin is active.

Troubleshooting

  • Alerts, retention or vault syncs never run: they depend on WP-Cron, which only runs when the site receives traffic. If DISABLE_WP_CRON is set or traffic is low, call wp-cron.php from a real cron job (for example every 5 minutes) or run wp cron event run --due-now. System Health shows whether the maintenance hook is scheduled.
  • An alert shows "failed" in the Alert Center: read the stored response message. Webhook URLs must be public https:// URLs; private or local addresses are refused.
  • S3 vault: "Access Denied": the key needs s3:PutObject and s3:DeleteObject on the bucket/prefix (the connection test writes and deletes a probe object), plus s3:AbortMultipartUpload for packages over 8 MiB, which use multipart upload (initiating, uploading parts and completing are covered by s3:PutObject; a failed multipart upload is aborted). For non-AWS providers, enter the provider's endpoint and enable path-style addressing if required. Self-hosted endpoints on private networks are blocked unless the tbsh_cal_allow_private_vault_endpoints filter returns true.
  • Plain FTP vault stopped working: plain FTP sends the password unencrypted and is turned off. Edit the vault and choose FTPS (a developer can re-enable plain FTP on a closed network with the tbsh_cal_allow_plain_ftp filter).
  • FTPS vault is unavailable: the PHP ftp extension is not installed on the server (System Health reports this). Use an S3-compatible or remote-site vault, or ask your host to enable it.
  • Private files are publicly readable (nginx): nginx ignores .htaccess. Add a deny rule; System Health reports a failure while files in uploads/tbsh-compliance-private/ can be downloaded.
    nginx 
    location ^~ /wp-content/uploads/tbsh-compliance-private/ {
    deny all;
}
  • Stored credentials stopped working: the WordPress salts or TBSH_CAL_ENCRYPTION_KEY changed. Re-enter the credentials, and define TBSH_CAL_ENCRYPTION_KEY to avoid this in future.
  • Vault package cannot be decrypted: check the passphrase and that the file was fully downloaded; any modified chunk fails authentication.
  • Vault sync says the passphrase is missing: every vault needs its own encryption passphrase before it can sync.
  • Large vault packages are slow to build: install the PHP sodium extension; without it the slower compatibility library is used.
  • AI analysis is unavailable: choose a provider, a model (required for OpenAI, Gemini and OpenAI-compatible endpoints) and an API key or endpoint in Settings.
